# Xi 上下文策略 A/B 实验

## 实验问题

对于仓库级代码修复任务，预先注入受限仓库地图（`repo-map`）能否比模型按需搜索
（`search`）减少探索成本，同时保持任务成功率？

## 实验设置

- 评测集：Xi Core Benchmark Suite，共 5 类 Python Bug；
- 策略：`search` 与 `repo-map`；
- 模式：同一真实模型、相同工具、相同 Case 顺序与评分标准；
- 重复次数：每种策略 3 轮，共 30 个 Case 执行；
- 顺序控制：每轮轮换首发策略，降低固定先后顺序带来的偏差；
- 统计指标：Case/Suite 成功率、步骤、工具调用、Token、上下文字符数和耗时。

## 实验结果

| 策略 | Case 成功率 | Suite 完整通过率 | 平均步骤 | 平均工具调用 | 平均总 Token | 平均耗时 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| `search` | 100.00%（15/15） | 100.00%（3/3） | 21.67 | 29.33 | 47,289 | 201.62s |
| `repo-map` | 93.33%（14/15） | 66.67%（2/3） | 19.00 | 26.00 | 45,180 | 200.18s |

在这组小规模实验中，`repo-map` 相比 `search`：

- 平均步骤减少约 12.3%；
- 平均工具调用减少约 11.4%；
- 平均总 Token 减少约 4.5%；
- 但出现一次失败，因此当前不能宣称其整体效果优于 `search`。

## 失败分析与运行时改进

唯一失败并非补丁方向错误，而是模型在读取文件后只回复“接下来修改并测试”，没有实际
调用修改和验证工具，旧 Runtime 却把这段文本当作任务完成。

为此，Xi 增加了证据驱动的 `CompletionContract`：Benchmark 中只有在产生成功文件修改，
并且最后一次修改后成功执行指定验证命令时，Runtime 才接受最终回答。缺少证据时，
Runtime 会把缺失项反馈给模型并继续循环。

改进完成后，对原失败 Case 进行了一次真实模型聚焦复测，结果通过。该复测用于验证运行时
修复，不与原三轮 A/B 聚合数据混合，也不能替代重新运行完整实验。

## 当前结论

`repo-map` 展现了减少探索步骤和工具调用的潜力，但现有样本量不足，且上下文字符数更高。
下一阶段应扩大任务规模，并进一步记录首次定位正确文件所需步骤、无效读取次数和补丁大小，
再判断仓库地图是否具有稳定收益。

原始 Trace、模型输出和本地绝对路径保存在 `.xi/` 下，不提交到公开仓库；本文只保留脱敏后的
方法、聚合指标和可复核结论。
